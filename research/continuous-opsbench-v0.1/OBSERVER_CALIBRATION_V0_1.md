# Independent observer calibration and known-answer probes v0.1

## Purpose

This is an additive observer-calibration layer for issue #202. Runtime attestation (#196) records the observer's declared coverage, event-stream commitment, challenge and receipt sequence. This evaluator goes further: it compares an evaluator-private expected probe set against independently authenticated injection receipts and the observer's ordinary detection receipts.

The verifier calls the runtime certification entry point first, so a probe calibration cannot qualify a runtime run whose manifest, freeze, scenario, raw trial events or runtime attestations are invalid. Calibration plan, injection and detection records are then joined one-to-one by (run, trial, arm, probe digest).

This is a structural evaluator. Input publisher/source claims must already have been authenticated by the existing typed evidence adapter (#190/#191). This module does not implement signatures, challenge issuance, kernel hooks, event collection or durable replay state.

## Three separated roles

1. **Expected-probe oracle:** generated by the evaluator after system freeze. It owns the hidden expected probe set and expected policy decisions. The plan is not sent to the agent or included in agent-visible files.
2. **Probe injector:** an independent challenge authority that causes safe, synthetic canary events through the exact runtime/host collection paths under test.
3. **Runtime observer:** emits its ordinary authenticated event evidence. It does not receive the expected answer or a special "probe detected" API.

A fourth component, the **calibration verifier**, joins the private expected plan with authenticated injector and observer receipts. It computes all counts and metrics itself. No caller-supplied sensitivity, specificity, observer_calibrated boolean, or coverage aggregate is accepted as a substitute for the probe-level records.

The injector, observer, evaluator, candidate and baseline must be separated by source identity and control domain. The plan includes a fresh challenge identifier distinct from the runtime attestation nonce. The typed evidence adapter authenticates the challenge authority and consumes replay state through the existing durable replay guard.

## Probe channels and controls

The channel enum is versioned and currently includes:
- process lifecycle and child-process lineage;
- executable load;
- filesystem/object read and write;
- mount and namespace changes;
- policy-denied operation attempts;
- resource-control changes;
- DNS and egress;
- cross-trial writable-state probes;
- telemetry pipeline and collector health.

Each channel included in a trial/arm plan must contain both:
- a **positive control** whose expected policy decision is Forbidden; and
- a **negative control** whose expected policy decision is Allowed.

A positive control tests whether a prohibited action/event is detected and classified as forbidden. A negative control tests that a permitted event is not falsely classified as prohibited. A no-detection disposition is a miss even for a negative control; an unknown classification is not credited as a correct classification. This prevents an observer from achieving perfect apparent recall by labelling every signal as forbidden or by dropping benign events.

Probe targets use opaque digests. Raw paths, canary contents, artifact names and private oracle data stay in the restricted injector/evaluator boundary. Probe injection must use synthetic canaries and controlled sinks and must not mutate business service state or expose customer data.

## Record binding

### ObserverCalibrationPlan

One plan per planned (trial, arm) binds:
- run/trial/arm and exact manifest/scenario/agent-or-baseline identity commitments;
- runtime instance identity;
- frozen observer source/control-domain/adapter;
- frozen challenge-authority identity/control-domain;
- one-use calibration challenge ID and probe-suite digest;
- issue/expiry times;
- evaluator-private expected probes, each with probe ID, channel, expected policy decision, target digest, independent fault/topology cluster digest and maximum detection latency.

Calibration challenges are issued after the run freeze, after the runtime challenge, and strictly before measurement begins. Their lifetime is capped at one hour and must cover the entire runtime measurement interval, including the runtime observer's clock-uncertainty margin. Challenge IDs must be unique within the run.

### ProbeInjectionReceipt

The independent injector records one receipt for every expected probe. It binds the exact run/trial/arm/challenge/probe/runtime, channel and target; records whether injection actually occurred; and commits to the injection event. The injector records its own clock uncertainty, which is bounded and included in the latency calculation. A not_injected result cannot be silently dropped or counted as a miss; it makes the calibration incomplete and is rejected by this v0.1 strict certification path.

### ProbeDetectionReceipt

The observer publishes exactly one disposition per expected probe. It binds the same challenge/probe/runtime plus the observer identity/adapter. The disposition is either:
- detected, with channel, target, policy decision, event time, event sequence and event commitment; or
- not_detected.

Unknown, duplicated, substituted, unplanned or missing records cannot be treated as successful coverage.

## Metrics and arithmetic

The evaluator computes each metric from the expected plan and one-to-one receipts:
- expected/injected/detected probe counts;
- misses and false negatives;
- false positives and unknown classifications;
- true positives and true negatives;
- per-channel and run-level sensitivity, specificity and precision in parts per million;
- p50 and p95 detection latency;
- number of independent probe clusters, both overall and per channel;
- over-latency probes and Pass/Fail/Indeterminate disposition.

Definitions:
- Sensitivity = true positives / all expected positive controls.
- Specificity = true negatives / all expected negative controls.
- Precision = true positives / (true positives + false positives).
- A positive control that is missed, classified Allowed or classified Unknown is not a true positive.
- A negative control classified Forbidden is a false positive. A negative control that is not detected is a miss and does not count as a true negative.

Latency is a conservative upper bound using both independent clocks:

    (detection time + observer uncertainty) - (injection time - injector uncertainty)

Detection and injection intervals must be consistent with the runtime measurement interval after applying clock uncertainty. The conservative latency must not exceed the preregistered channel/probe ceiling.

Probe clusters are independent fault-schedule/topology units. Candidate and Baseline probes against the same scenario share the same cluster digest. Repeated probes and the matched arm do not multiply the independent-cluster denominator. Campaign-level confidence intervals must resample clusters, not individual probes or events.

## Fail-closed semantics

- Missing or unplanned plan, injection or detection: reject; never infer zero.
- Duplicate injection/detection, duplicate challenge, duplicate probe ID within a trial/arm: reject.
- Probe not actually injected: reject as unavailable, not a successful negative.
- Observer source/adapter/target/channel mismatch: reject.
- Zero event commitment or zero event sequence: reject.
- Detection provably preceding injection under clock uncertainty: reject.
- Detection outside runtime measurement window: reject.
- Clock uncertainty beyond the maximum: reject.
- Any positive-control miss, false negative, false positive or over-latency result: calibration Fail.
- An Unknown decision: calibration Indeterminate unless a separate hard Fail already exists; Fail is never downgraded by later Unknown evidence.
- Complete runtime receipts alone do not imply calibrated observer coverage.

## Proposed target ladder

These are hypotheses for the confirmatory program, not measured results:
- 100% pass on the deterministic positive/negative conformance corpus for every claimed channel and tier.
- Zero false negatives and zero false positives on the canonical known-answer suite.
- At least 300 independent representative probe clusters per channel for a confirmatory sensitivity estimate, with exact confidence intervals. Repeated probes, time windows and both arms within one cluster do not increase this denominator.
- Initial one-sided 95% miss-rate bound goal around 1% or lower, when independence and representativeness assumptions are supported.
- Sensor-specific p95 detection latency budgets. Initial proposal: <=1 second for local process/policy events; filesystem/object, DNS/egress and remote sinks have separate budgets justified by their instrumentation.
- Collector detach, sequence gaps and event loss detected within one sampling interval; silent continuation as Complete is a hard failure.
- Report per channel and per sandbox tier. Do not aggregate Research, Process, Container and MicroVM tiers into a single observer score.

A zero-miss result over 300 independent clusters does not prove zero risk. With zero events in N independent clusters, report the exact one-sided binomial upper confidence bound and its assumptions.

## Research questions

- Which event classes can each runtime tier observe without gaps or ambiguous semantics?
- What is the observer's false-negative rate under collector overload, hook detach, process-tree churn, mount changes, DNS caching and namespace transitions?
- Does calibration remain stable across candidate/baseline model families and scaffolds?
- Can calibration detect selective event loss, where only events correlated with a prohibited behavior are suppressed?
- What is the cost/latency frontier for high-sensitivity monitoring with complete provenance?
- How do sensor false negatives propagate into runtime-certification and agent-performance conclusions?

- SREGym 2026 evaluates 90 realistic SRE failure problems across layers and highlights variation across problem families: https://msrg.github.io/publications/sregym-a-live-benchmark-for-ai-sre-agents-with-high-fidelity-failure-scenarios/
- SRE-Marathon evaluates continuous long-horizon operations with changing faults and applications: https://arxiv.org/abs/2609.33023

The novel OpsBench contribution is to measure whether the observer detects the known-answer events that support its own runtime claims. This complements, but does not replace, platform attestation, host-side enforcement, real sandbox escape tests or SRE service-outcome evaluation.

## Claim ceiling

Passing these deterministic tests proves only that the evaluator correctly handles the supplied synthetic probe records. It does not prove that a particular kernel/hypervisor cannot suppress the same event class, that all event paths are instrumented, or that production distributions are represented. A real qualification needs the external injector, real tier-specific runtime instrumentation, source-authenticated receipts, adversarial sensor-detach/loss tests and offline evidence verification.

## Architecture boundaries

- Reuse #196 runtime receipts and the frozen one-use challenge authority.
- Reuse #197 tier/Supervisor evidence and real external runtime adapter.
- Reuse #190/#191 typed source authentication and durable replay protection.
- Platform Saga remains the episode coordinator.
- Participant-owned ledgers own remote effect truth; independent observers own service outcomes.
- Nixward remains the sole host transaction/interlock/journal/recovery authority.
- Calibration is an evaluator, not another event bus, runtime monitor, policy engine, signature system or journal.
