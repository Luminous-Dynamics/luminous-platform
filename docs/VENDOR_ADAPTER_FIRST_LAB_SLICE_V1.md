# Vendor Adapter First Lab Slice v1

**State:** execution runbook / acceptance contract; no adapter or physical device is qualified by this document.  
**Related:** [Issue #23](https://github.com/Luminous-Dynamics/luminous-platform/issues/23), [adapter execution contract](VENDOR_ADAPTER_EXECUTION_CONTRACT_V1.md), [endpoint and credential boundary](VENDOR_MANAGEMENT_ENDPOINT_SECURITY_V1.md), [capability registry](../security/vendor-adapter-capability-registry-v1.json).

## Purpose

Turn the global vendor-adapter roadmap into one bounded, reviewable work case. The first slice must prove that the platform can identify one explicitly authorized lab target, collect a read-only observation, normalize it without inventing fields, and produce evidence that an independent checker can verify. It must not perform configuration mutation, firmware installation, recovery, or flashing.

The initial target is chosen from devices the project owner can lawfully administer and physically recover. Do not select a target solely because its vendor name appears in the registry. Prefer a device with a documented API, stable identity fields, a recoverable lab network path, and no production dependency.

## Gate 0 — target admission

Record the following before writing an adapter:

- Asset owner/authority and the explicit lab-only scope of permission.
- Vendor, product family, exact model, hardware revision, serial/asset reference (store the raw value only in protected local evidence), software/firmware version, management method, and relevant region/endpoint profile.
- Physical recovery method, console/out-of-band access, backup location, and the person responsible for stopping the exercise.
- Authoritative vendor documentation URLs and access date for each intended read operation.
- Data classification and retention location for raw output; identify fields that must be redacted before normalized evidence leaves the customer-controlled store.

**Reject admission** if the exact target identity is ambiguous, authority is not evidenced, recovery is unavailable, credentials cannot be scoped to read-only access, or vendor/API terms and endpoint semantics are unresolved.

## Gate 1 — minimum adapter contract

The first adapter slice implements only these operations:

1. `inventory_read`: identify the exact target and return only observed fields.
2. `health_read`: return supported health observations, with unsupported and unknown distinct.
3. `version_read`: return exact software/firmware identifiers as reported by the device.
4. `entitlement_read` and `lifecycle_read`: only where authoritative documented sources are available; otherwise declare unsupported with a reason.

Every response includes:

- contract version and adapter source revision;
- target identity binding and endpoint-profile revision;
- observation timestamp and clock/collection limitations;
- source method and redaction profile revision;
- per-field provenance and state: `observed`, `unsupported`, `unknown`, or `error`;
- bounded diagnostic code, never a credential, raw secret, or unredacted configuration;
- evidence references and content digests for protected raw artifacts.

Do not convert missing fields to empty strings, zero, false, or a healthy state. An API timeout is `error`, not “no update available” or “unsupported.” Do not infer a device model from a vendor family name.

## Gate 2 — deterministic conformance corpus

Create checked-in synthetic fixtures and tests for each operation:

- complete normal response;
- optional field omitted by the vendor;
- explicit null / empty response;
- unknown future enum or additional vendor field;
- malformed response and invalid encoding;
- authentication denied / credential revoked;
- rate limited with retry-after;
- timeout before response and timeout after request dispatch;
- stale or contradictory identity;
- endpoint redirect/origin change;
- pagination truncation or duplicate records, where applicable;
- redaction of credential-shaped values and customer topology;
- unsupported capability with a non-empty rationale.

Use a separately authored expected-output oracle: expected normalized records must not be generated by the adapter under test. Tests must assert both positive facts and forbidden inferences. Keep fixtures synthetic unless there is a documented authorization and redaction review for captured output.

Read-only retries are bounded and respect vendor rate limits. No mutating operation is in this tranche; future mutation support must use a separate contract and effect journal rather than widening this adapter implicitly.

## Gate 3 — independent evidence verification

The independent verifier receives a frozen evidence manifest, not a live adapter object. It verifies:

- manifest and artifact digests;
- schema and contract versions;
- exact source revision and target scope;
- timestamp format, ordering, and freshness bounds;
- provenance for each asserted field;
- redaction and privacy assertions;
- expected-versus-observed conformance results;
- that unsupported/unknown/error states have not been promoted to success;
- that the adapter implementation is not the verifier identity.

A valid signature or digest proves integrity relative to the referenced bytes; it does not prove that the device truthfully reported its state. Record that limitation explicitly.

## Evidence packet

One run produces an immutable packet containing:

1. target admission record and authority reference;
2. pinned adapter revision and dependency/environment description;
3. vendor documentation references and access date;
4. synthetic fixture corpus revision and independently authored expected outputs;
5. raw artifact digests plus protected storage references (no raw secrets in the shared record);
6. normalized observations and field provenance;
7. test command, discovered case count, exit status, and machine-readable report;
8. independent verifier revision, result, and findings;
9. unresolved limitations, failures, and follow-up items;
10. exact repository commit and evidence-manifest digest.

A queued workflow, missing job record, empty test discovery, static source audit, schema parse, or mock-only result must never be represented as a passing physical-device test.

## Maturity decision

Use these states independently for each exact adapter operation and exact target scope:

- **A0_DISCOVERED:** research and source references only.
- **A1_READ_ONLY_TESTED:** deterministic synthetic tests pass and the test corpus is reviewable.
- **A2_STATE_CONTRACT_TESTED:** target identity, state normalization, provenance and independent evidence verification are exercised against an authorized lab target.
- **A3_CHANGE_QUALIFIED:** separate low-risk change contract, authorization binding, effect journal and recovery validation are complete.
- **A4_FIRMWARE_RECOVERY_QUALIFIED:** exact image/model/entitlement and recovery gates are validated on non-production hardware.
- **A5_SERVICEABLE:** operational monitoring, support boundaries, incident response, maintenance ownership and customer-facing limitations are documented.

A higher-level maturity label never upgrades an operation or model that lacks its own evidence. Passing synthetic tests alone cannot establish A2 or higher. No global vendor-family qualification is implied.

## Stop conditions

Stop the exercise and preserve evidence if target identity changes, the endpoint redirects outside its approved origin, authorization is stale, a read unexpectedly mutates state, output includes unredacted secrets, rate limits are exceeded, observations conflict, or the verifier cannot reproduce the packet result. Do not “fix” a failed observation by weakening the schema or changing expected output after seeing the result; revise the contract with a new version and retain the old result.

## Immediate next action

Select one owner-authorized, physically recoverable lab device; complete Gate 0; then implement one read-only operation end to end. Keep other vendor adapters at A0 until each has its own target, fixtures, evidence packet, and independently verified scope.
