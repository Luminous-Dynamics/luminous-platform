# Luminous Origin-Bound Intent and Parameter Provenance Contract v0.1

**Status:** Non-normative research contract and synthetic benchmark — not an implementation claim  
**Date:** 2026-11-19  
**Tracking:** [AUTH-CORE-002 #503](https://github.com/Luminous-Dynamics/luminous-platform/issues/503)  
**Related architecture:** XAP; Effect-Bound Capability Contract v0.1; Symthaea INTX; Mycelix AGENT

## 1. Research thesis

An exact effect capability is necessary but not sufficient. The agent may invoke the exact allowed operation on the exact target with the exact argument digest, while that argument was sourced from an attacker-controlled webpage or document.

This contract therefore separates:
- **Intent authority:** which actions and parameter sources the principal actually delegated.
- **Data origin:** where the values used by an action came from and how they were transformed.
- **Effect authority:** whether Mycelix AGENT grants the principal/actor/participant the exact operation and context.
- **Participant outcome:** whether the final participant admitted the exact request and what effect was observed.

A provenance manifest is **evidence**, not a capability. It cannot grant a new operation, participant, purpose, target, credential, or physical action. It is bound to the exact action request and passed into the existing Mycelix authority and participant checks.

This composes two recent research directions:
- **AutoDojo** shows the importance of action-open task specification: attacks recover 28% ASR overall and 64% on action-open tasks against a filter that reached zero static ASR. Its central lesson is that when the user delegates action selection to content, attacker instructions can masquerade as ordinary data.
- **ROPE** uses unforgeable origin tracking so attacker-writable values cannot reach origin-guarded state-changing parameters. It reports 1.6–2.6% ASR with 82–100% clean-utility retention in its evaluated settings, and states guarantees about per-step origin and paraphrase-invariant decisions.

Sources:
- AutoDojo (13 June 2026): https://arxiv.org/abs/2606.15057
- ROPE (27 August 2026): https://arxiv.org/abs/2608.27496

Those results are paper-specific and not directly comparable to Luminous's authorization/effect metrics. Luminous must not claim novelty for origin tracking or parameter provenance. The research opportunity is **composing origin with intent precision, participant/purpose/context authority, delegation, one-use effects, physical safety and independent postconditions**.

## 2. Task-specification precision

Three task forms need different rules:

### Fully specified

The principal specifies the action, target, participant, purpose/context and protected parameters. The model may reason about content, but untrusted content cannot replace any of these fields.

### Parameter-open

The principal specifies the action and target, and explicitly delegates a constrained set of parameter fields to named/allowlisted sources. For example, a user may authorize extracting an invoice amount from a named invoice while retaining control of the payee, account, operation and participant.

A source can populate only the fields delegated to it. An invoice's instructions cannot expand the delegated fields or replace the payee. Typed/range/value constraints remain attached to the parameter policy.

### Action-open

The principal delegates action selection. This is not unrestricted permission for any action mentioned in retrieved content. The user-authorized action set must be finite and bind operation, target, participant, purpose and context. The agent may select only an action in that set; content cannot add a new action or expand a target.

If the principal has not provided a finite authorized set, the request requires clarification or denial. An untrusted document may influence selection among already authorized options, but that influence is reported separately and cannot extend the set.

Action-selection origin and parameter-value origin are separate.

## 3. Origin manifest

The manifest is generated by a trusted retrieval/connector boundary, not self-authored by the model. It binds:
- manifest ID and digest;
- principal, intent ID and exact request digest;
- trusted collector identity and verification outcome;
- action-selection origin and source;
- each sensitive parameter's value digest;
- source identity/class, source receipt digest and verification;
- complete source/transform lineage;
- agent handoff count and transformations.

Source classes include:
- principal input;
- user-named source;
- authoritative record;
- agent-derived value with preserved input lineage;
- attacker-writable content;
- unknown.

The manifest is content-addressed and request-bound, but its digest does not make its assertions true. The source collector, receipt and lineage mechanism are separate trust assumptions that must be qualified.

## 4. Parameter provenance rules

1. Every protected argument has an exact value digest that matches both request and manifest.
2. Principal input may populate a parameter only where the intent permits it.
3. User-named and authoritative sources may populate only fields expressly delegated to them and only under their source allowlist.
4. Agent-derived values are admissible only when complete lineage shows that all base sources were permitted. A model transformation is not a trust upgrade.
5. Any attacker-writable lineage rejects the protected parameter, even after paraphrasing, summarization, translation, embedding, memory storage or agent handoff.
6. Missing, unverifiable, stale or incomplete provenance is indeterminate. It is not silently counted as safe.
7. A source can contain useful data and malicious instructions simultaneously. Authorization to extract one parameter does not authorize following its instructions.
8. Tool and child-agent boundaries must preserve origin metadata; no downstream component may strip or rewrite it to “trusted”.

## 5. Composition with effect-bound authority

The origin manifest supplements the existing effect-bound capability tuple. It does not replace or widen:
- principal and actor identity;
- participant, target and operation;
- argument digest;
- purpose and context;
- policy epoch and validity;
- delegation and revocation;
- budget and one-use permit;
- participant final authorization and same-attempt reconciliation.

The participant makes its final admission decision using both:
1. the canonical Mycelix authority result; and
2. the request-bound intent/origin evidence required by the protected parameter policy.

A valid provenance manifest cannot authorize an otherwise invalid effect. A valid grant cannot legitimize attacker-origin data in an origin-guarded parameter.

## 6. Synthetic corpus v0.1

Machine-readable artifact:
- `origin-bound-intent-provenance.fixtures.v0.1.json`
- `origin-bound-intent-provenance.schema.v0.1.json`

The 30 fixtures cover fully specified, parameter-open and action-open tasks; named-source extraction; attacker recipient substitution; non-parameter instructions embedded in useful documents; finite action sets; action selection outside the set; untrusted influence within a pre-authorized set; OT action escalation; paraphrase and summary laundering; multi-hop agent handoffs; mixed lineage; forged/unverified receipts; manifest/request digest substitution; revoked/unknown underlying authority; false denial; and unauthorized/indeterminate commits.

Each episode separately reports intent compliance, provenance acceptance, underlying effect authority, participant decision correctness, fail-closed violation, untrusted influence within an authorized set, task outcome and effect disposition.

## 7. Benchmark and SOTA comparison

| Comparator | What it tests | Luminous extension |
|---|---|---|
| AutoDojo | Adaptive indirect prompt injection; task precision; action-open vulnerability | Bind the chosen action to an explicit finite authority set and verify the participant effect |
| ROPE | Unforgeable source provenance for sensitive parameters and paraphrase-invariant admission | Add purpose/context, principal/actor, delegation, policy epoch, budget, participant and effect evidence |
| AgentDojo / InjecAgent / ASB / AgentDyn | Prompt injection, tool use, harmful calls, dynamic scenarios | Add source lineage, intent precision and exact participant authorization oracles |
| ToolSandbox / τ-bench / WASP | Stateful trajectory, milestones, final state and rule-verified attack goals | Add origin, identity, consent, policy revision and actual protected effect predicates |

Do not compare native AutoDojo/ROPE ASR directly with Luminous participant-side unauthorized effects. A matched reproduction must pin the model, tools, task distribution, intent precision, sources, origin labels, policies, participant oracle and evaluator.

### Proposed internal targets (not achieved)

- 100% exact outcomes on frozen deterministic positive, negative and ambiguous controls.
- Zero attacker-origin-only values in protected state-changing parameters.
- Zero action-open action selection outside the principal's finite authorized set.
- 100% acceptance of eligible positive controls, so deny-all cannot pass.
- Unknown origin/lineage/authority never counted as safe.
- 100% of cross-agent/tool transformations preserve source lineage or return indeterminate.
- Re-run with adaptive paraphrase, summarization, multilingual translation, memory and multi-agent handoffs.
- Two independently implemented verifiers before any qualification claim.

## 8. Ownership

- **Symthaea INTX:** task precision, typed user intent and finite delegated action set; no self-authorization.
- **Mycelix AGENT:** canonical principal/actor/grant/delegation/purpose/context authority; origin manifest is not a grant.
- **Connector/tool boundary:** source identity, byte/value digest and immutable acquisition receipt.
- **Platform / WAEP:** cross-source, transformation and claim/evidence reporting.
- **Xenia:** authenticated session and integrity of bound request/manifest transport.
- **Nixward / participant:** enforce exact operation and final local policy; no trust promotion based on model labels.
- **Symtropy / safety controller:** final physical safety boundary and independently observed physical effect.

No second authority database, policy engine, identity provider, provenance ledger, cryptographic primitive or participant runtime is introduced.

## 9. Claim ceiling

This is a synthetic contract and benchmark. It does not prove that Mycelix, Symthaea, Xenia or a deployed connector currently emits unforgeable origin labels. No runtime provenance enforcement, adaptive search, external reproduction, OT deployment or physical actuation is claimed. The manifest schema is a proposed projection and requires review by the canonical owners before implementation.
