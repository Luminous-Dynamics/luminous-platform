# SRQ durable single-use challenge ledger — research prototype

**Not a production authorization service or release qualification.** This Linux-only Rust prototype demonstrates one narrow property: an issued challenge bound to a transaction, target, plan, artifact and policy can be durably consumed at most once by concurrent callers that share the same protected local ledger.

## Why this is the next paradigm shift

The causal-integrity PRs test whether lifecycle records agree. This prototype adds a stateful security property that static JSON checks cannot establish: replay prevention across concurrent submissions and process restarts.

The ledger uses:
- a private parent directory and a mode-0600 regular journal file, rejecting symlink opens and hard-linked journals;
- Linux flock(LOCK_EX) to serialize callers across processes and threads;
- a closed append-only journal format, with version, exact field counts and strict digest/timestamp parsing;
- sync_all before reporting issue/consume success, plus a parent-directory sync at initialization;
- fail-closed behavior on an incomplete trailing record, malformed journal, binding mismatch, expiry, or duplicate consume.

The challenge ID is expected to be 32 bytes of cryptographic randomness encoded as lowercase hex, generated by the caller. This crate checks the representation but does not generate entropy. The caller must verify the signed authorization and independently compare its signed target/plan/artifact/policy binding before calling consume.

## Execute and benchmark

From the repository root:

    cargo fmt --manifest-path benchmarks/srq-lifecycle-interop/challenge-ledger-rs/Cargo.toml --all -- --check
    cargo test --locked --manifest-path benchmarks/srq-lifecycle-interop/challenge-ledger-rs/Cargo.toml
    cargo clippy --locked --manifest-path benchmarks/srq-lifecycle-interop/challenge-ledger-rs/Cargo.toml --all-targets -- -D warnings
    cargo run --locked --manifest-path benchmarks/srq-lifecycle-interop/challenge-ledger-rs/Cargo.toml --bin replay-benchmark

The benchmark races 64 callers against one challenge and reports acceptance/replay counts, concurrent-window duration, p50/p95/p99 operation latency, and aggregate submissions/second. Its intended result is exactly one accepted consumption, 63 replay rejections, zero unexpected errors, and rejection after reopening the ledger. Timing is a workload-specific observation, not a universal SOTA comparison. CI retains a JSON report bound to the exact source revision, source digests, and toolchain version.

## Current guarantees and non-guarantees

- **In scope:** serialized single-use consumption within one local protected journal; exact transaction/target/plan/artifact/policy matching; bounded challenge lifetime based on a caller-provided clock; fail-closed parsing; durable-sync-before-return semantics; concurrency and restart tests.
- **Not implemented:** Ed25519 or other signature verification, key trust/revocation, CSPRNG generation, remote challenge issuance, hardware-backed monotonic counters, trusted wall clock, remote transparency, anti-rollback protection for restoration of an old complete journal, or actual NixOS execution/recovery.
- **Storage rollback remains a critical limitation:** a local actor able to replace the journal with an earlier valid copy can roll back the consumed set. Production deployment needs a protected monotonic anchor, remote state service, hardware-backed counter, or another independently enforced anti-rollback mechanism.
- **Crash safety is conservative:** if consumption is synced but the caller crashes before the privileged side effect, the operation may not happen. Retrying the same challenge is rejected; the caller must obtain a fresh challenge and reauthorize. This avoids claiming end-to-end exactly-once execution across a non-transactional external side effect.
- **Power-loss claims are not made:** unit tests and the CI filesystem exercise process-level behavior, not physical power-loss durability or storage-device guarantees.

## Industry alignment

[RFC 9334 / RATS §10](https://www.rfc-editor.org/rfc/rfc9334.html#section-10) describes nonce, timestamp and epoch-based freshness, including the trade-off that nonce-based approaches require per-challenge state. The ledger is a prototype for that stateful single-use part, not a complete RATS implementation. [TUF](https://theupdateframework.github.io/specification/) remains the reference for secure update metadata, rollback and freeze defenses; this local ledger does not replace TUF or solve journal rollback on its own.

## Acceptance criteria

The exact-head CI gate must pass formatting, tests and Clippy; 64 concurrent submissions must produce exactly one successful consume and 63 AlreadyConsumed responses; the consumed state must survive reopening; malformed partial records and altered bindings must fail closed. Every report remains qualification_status=BLOCKED and claim_ceiling=none.
